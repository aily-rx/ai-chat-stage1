# Prompt 样例 01：正式风格公文对话

| 项目 | 内容 |
|---|---|
| Prompt ID | `chat-formal` |
| Prompt 版本 | `v1.0` |
| 实际模板 | `backend/src/main/resources/prompts/chat-base.txt` + `chat-formal.txt` |
| 调用接口 | `POST /api/chat/stream`，`style=formal` |
| 模型 | `deepseek-chat`（可通过 `LLM_MODEL` 配置） |
| 适用场景 | 公文写作、制度说明、需要完整结构和正式语气的问答 |

## 1. 场景与目标

用户需要一份正式风格的公文内容或一段规范的公文知识回答。目标是：

- 使用规范书面语，结构完整，语气庄重克制。
- 需要时给出标题、称谓、正文、结尾和落款。
- 不编造单位、数据或文件依据；信息不足时用占位符表达。
- 直接输出正文，不解释写作过程。

该 Prompt 用于阶段一的流式对话演示。前端通过 `style=formal` 选择本模板，后端用 `SseEmitter` 将模型增量内容转发给浏览器。

## 2. 系统提示词

### 2.1 基础模板 `chat-base.txt`

```text
你是一名严谨的中文公文写作助手，请根据用户的写作要求输出中文内容。
要求：
1. 内容准确、结构清晰，符合中文公文表达习惯；
2. 使用 Markdown 分段，必要时使用标题、编号和列表；
3. 不要编造不存在的单位、数据或文件依据，缺失信息使用“XX单位”等占位符；
4. 直接输出正文，不要解释你的写作过程。

{{style_instruction}}
```

### 2.2 正式风格片段 `chat-formal.txt`

```text
风格要求：正式。使用规范书面语和完整公文结构，称谓、开头、正文、结尾和落款按需完整呈现，语气庄重克制。
问答类回答通常控制在 200–300 字；撰写公文时按实际需要完整展开。
```

### 2.3 渲染结果

`PromptService` 在启动时读取两个文件，把 `{{style_instruction}}` 替换为正式风格片段。实际发给模型的 system prompt 是：

```text
你是一名严谨的中文公文写作助手，请根据用户的写作要求输出中文内容。
要求：
1. 内容准确、结构清晰，符合中文公文表达习惯；
2. 使用 Markdown 分段，必要时使用标题、编号和列表；
3. 不要编造不存在的单位、数据或文件依据，缺失信息使用“XX单位”等占位符；
4. 直接输出正文，不要解释你的写作过程。

风格要求：正式。使用规范书面语和完整公文结构，称谓、开头、正文、结尾和落款按需完整呈现，语气庄重克制。
问答类回答通常控制在 200–300 字；撰写公文时按实际需要完整展开。
```

## 3. 变量说明

| 变量或参数 | 来源 | 作用 | 示例 |
|---|---|---|---|
| `{{style_instruction}}` | 服务端加载 `chat-formal.txt` 后替换 | 将风格要求注入基础模板 | 正式风格片段 |
| `message` | 请求体 | 作为 `user` role 的消息发送，不拼接到 system prompt | `介绍一下RAG` |
| `style` | 请求体 | 选择 Prompt 模板，正式模式必须为 `formal` | `formal` |
| Prompt 版本 | `prompt-catalog.properties` | 写入加载日志和请求完成日志 | `v1.0` |

说明：阶段一没有把用户正文直接嵌入 system prompt。用户消息通过 OpenAI 兼容协议的 `messages[].role=user` 传入，避免用户输入改变系统约束。

## 4. 模型参数

当前后端实际请求参数：

| 参数 | 当前值 | 说明 |
|---|---|---|
| `model` | `deepseek-chat` | 从 `LLM_MODEL` 读取，未配置时使用该默认值 |
| `stream` | `true` | 流式对话接口 |
| `temperature` | 未显式设置 | 使用 DeepSeek API 默认值；阶段一没有为了演示随意调参 |
| `max_tokens` | 未显式设置 | 使用模型默认输出限制 |
| 连接超时 | 10 s | `HttpClient` 连接超时 |
| 流式总超时 | 不设置整体超时 | 由客户端停止或上游结束控制，避免长回答被固定时长截断 |

如果后续需要更稳定的结构化输出，可以在模型调用层统一增加 `temperature` 等参数；这属于新的变更，不应只改 Prompt 文档。

## 5. 示例输入与输出

### 5.1 示例一：知识问答

输入：

```json
{
  "message": "介绍一下RAG",
  "style": "formal"
}
```

真实联调输出节选：

```text
## RAG（检索增强生成）简介
RAG 是一种将信息检索与文本生成相结合的技术架构……
**基本流程**
1. 索引构建……
2. 检索……
3. 增强生成……
```

测试记录：首字约 0.51 s，总耗时约 2.05 s，输出约 417 字符，结束事件为 `done`。

### 5.2 示例二：短问题也保留完整结构

输入：

```json
{
  "message": "用三句话介绍RAG",
  "style": "formal"
}
```

真实联调输出节选：

```text
# 关于RAG技术的介绍

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将信息检索与大语言模型生成能力相结合的技术架构。其基本思路是：在模型生成回答前，先从外部知识库中检索与问题相关的文档片段，……
```

测试记录：首字约 1.44 s，总耗时约 2.89 s，输出约 420 字符，traceId 为 `8675dd58`。

## 6. 设计理由

1. **角色和任务分开写**：先说明“中文公文写作助手”，再说明输出要求，避免模型把任务理解成闲聊。
2. **不编造约束放在基础模板**：正式问答和公文写作都可能出现单位、日期、依据缺失，必须统一限制。
3. **风格片段独立**：正式与简洁共享同一套基础约束，只替换 `{{style_instruction}}`，避免两份 Prompt 逐渐漂移。
4. **要求直接输出正文**：公文页面不需要“好的，以下是……”这类过程性文本。
5. **Markdown 约束**：前端使用 marked + DOMPurify 渲染，合适的标题和编号能让公文结构更清楚。

## 7. 失败案例与改进

### 7.1 简化版 Prompt 的失败现象（对照案例）

如果把系统提示词简化成：

```text
你是公文写作助手，请根据用户要求写一份公文。
```

模型容易出现：

- 开头输出“好的，以下是一份通知：”。
- 结构依赖模型自由发挥，标题、主送、落款可能缺失。
- 缺少单位、数据时自行补造看似合理的信息。
- 用户要求正式风格时，回答仍可能过于口语化。

### 7.2 改进版本

当前模板增加了四类约束：

| 问题 | 改进 |
|---|---|
| 过程性解释 | “直接输出正文，不要解释你的写作过程” |
| 幻觉信息 | “不要编造不存在的单位、数据或文件依据，缺失信息使用 XX单位等占位符” |
| 风格不稳定 | 独立 `chat-formal.txt` 注入正式风格要求 |
| 结构不完整 | 要求按需呈现称谓、开头、正文、结尾和落款 |

该对照案例用于说明 Prompt 约束的作用，不代表某次线上请求的原始日志。阶段一实际联调中，模型流式返回和 Markdown 渲染均正常，相关真实记录见 `docs/streaming-test.md`。

## 8. 版本变更规则

- 修改 `chat-base.txt` 或 `chat-formal.txt` 后，必须同步更新 `prompt-catalog.properties` 中的 `chat.version`。
- 每次修改 Prompt 的提交标题使用 `fix(prompt)` 或 `feat(prompt)`，并在正文说明修改原因。
- 版本号变化会出现在启动日志和对话完成日志中，便于按 `promptVersion` 定位输出差异。
